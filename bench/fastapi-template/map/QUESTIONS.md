# Open questions from the flow map

Where independent runs disagreed. Each answer can be pinned in `decisions.json`.

## Split votes (placed by router-file affinity — please decide)

- `POST /users/signup`: sign-up vs sign-in → placed in **sign-in**

## Endpoints the runs put in different flows

- `POST /password-recovery-html-content/{email}` (`backend/app/api/routes/login.py:recover_password_html_content`): bu-1→recover-forgotten-password, bu-2→recover-forgotten-password, td-1→operate-deployment, td-2→recover-forgotten-password
- `POST /users/signup` (`backend/app/api/routes/users.py:register_user`): bu-1→sign-up, bu-2→sign-in, td-1→sign-in, td-2→sign-up

## Endpoints at least one run could not place in any flow

- `GET /items/{id}` — bu-2: No caller in the SPA or Playwright tests: the UI lists items via GET /items/ and never opens a single item (generated ItemsService.readItem is unused). Only reachable by direct API clients.
- `GET /users/{user_id}` — bu-2: No caller in the SPA or Playwright tests (generated UsersService.readUserById is unused); the admin table gets everything from GET /users/ and the current user from GET /users/me. Only reachable by direct API clients.
- `POST /private/users/` — bu-1: Test-only fixture: the private router is mounted only when FASTAPI_ENV == 'development' (backend/app/api/main.py), and its only caller is the Playwright helper frontend/tests/utils/privateApi.ts:createUser, which seeds users for E2E tests. No user-facing flow. It skips the duplicate-email check and accepts an is_verified field that User does not have.

## Busiest steps (hops ≥ 8)

- administer-users / **Admin creates a user with role and active flags, optionally emailing them their credentials** — 9 hops over 6 files

## Observations ("fighting the system"), by run

### bu-1 (bottom-up)
- User.hashed_password is written from five places that do not share one path: crud.create_user (signup, admin create, seed), crud.update_user (admin edit, reset-password), users.update_password_me inline (backend/app/api/routes/users.py:update_password_me), private.create_user inline (backend/app/api/routes/private.py:create_user), and a login-time rehash in crud.authenticate (backend/app/crud.py:authenticate).
- A read that writes: POST /login/access-token can commit a new password hash through backend/app/crud.py:authenticate when pwdlib's verify_and_update flags the stored hash for upgrade (bcrypt to argon2).
- Two ways to delete a user's items: backend/app/api/routes/users.py:delete_user issues an explicit bulk DELETE on Item before deleting the user, while backend/app/api/routes/users.py:delete_user_me relies on User.items cascade_delete and the FK ondelete=CASCADE in backend/app/models.py:Item.
- Two ways to update a user: admin edits go through backend/app/crud.py:update_user, but self-service profile and password updates mutate current_user inline in backend/app/api/routes/users.py:update_user_me and backend/app/api/routes/users.py:update_password_me. Email conflicts return 409 on update and 400 on create/signup.
- Dead duplication: backend/app/crud.py:create_item is used only by tests; backend/app/api/routes/items.py:create_item repeats the same logic inline.
- Superuser self-delete: frontend/src/routes/_layout/settings.tsx:UserSettings means to hide the Danger zone for superusers but uses tabsConfig.slice(0, 3) on a 3-element list, so it is shown. DELETE /users/me then returns 403 (backend/app/api/routes/users.py:delete_user_me), and the global frontend/src/main.tsx:handleApiError treats any 401/403 as an auth failure, clears the token and redirects to /login. The superuser is logged out instead of seeing the error. The same forced logout happens on item 403s ('Not enough permissions').
- Inconsistent email guard: backend/app/api/routes/users.py:create_user checks settings.emails_enabled before sending, but backend/app/api/routes/login.py:recover_password and backend/app/api/routes/utils.py:test_email call backend/app/utils.py:send_email, which asserts it. With SMTP unconfigured, password recovery returns 500 for registered emails and 200 for unknown ones, which undoes the anti-enumeration comment in recover_password.
- Auth tokens are stateless and never revoked: password reset tokens (backend/app/utils.py:generate_password_reset_token) are reusable for 48h and share SECRET_KEY/HS256 with access tokens without a type claim. Password change or reset leaves existing 8-day access tokens valid. Logout (frontend/src/hooks/useAuth.ts:useAuth) only deletes localStorage.
- backend/app/api/routes/login.py:recover_password_html_content hands an admin a working reset link for any user, which is effectively an admin account-takeover endpoint with no UI caller.
- The current user is fetched through two parallel paths: useAuth's React Query ['currentUser'] query (frontend/src/hooks/useAuth.ts:useAuth) and a direct UsersService.readUserMe call in the admin route guard (frontend/src/routes/_layout/admin.tsx:Route). POST /login/test-token (backend/app/api/routes/login.py:test_token) is a third, unused endpoint returning the same thing.
- backend/app/api/routes/utils.py:health_check returns a constant true, so the compose healthcheck that gates the backend never reflects database reachability.

### bu-2 (bottom-up)
- Global logout on any 403: frontend/src/main.tsx:handleApiError wipes localStorage['access_token'] and redirects to /login for every 401 AND 403 from any query or mutation, but the backend also uses 403 for plain authorization/business-rule refusals (backend/app/api/routes/users.py:delete_user_me 'Super users are not allowed to delete themselves', backend/app/api/routes/items.py:update_item 'Not enough permissions', backend/app/api/deps.py:get_current_active_superuser). A refused action therefore signs the user out.
- Superuser 'Delete Account' is offered then punished: frontend/src/routes/_layout/settings.tsx:UserSettings builds finalTabs with tabsConfig.slice(0, 3) for superusers, which is all three tabs (including danger-zone), so the filter is a no-op; the superuser can click Delete in frontend/src/components/UserSettings/DeleteConfirmation.tsx:DeleteConfirmation, backend/app/api/routes/users.py:delete_user_me returns 403, and handleApiError then logs them out.
- Password hashes are written from five places with different code: backend/app/crud.py:create_user, backend/app/crud.py:update_user (admin edit and reset-password), backend/app/api/routes/users.py:update_password_me (inline), backend/app/api/routes/private.py:create_user (inline, dev only), and backend/app/crud.py:authenticate (silent rehash during login, so a 'read-like' login writes User.hashed_password).
- Profile/email updates are split: backend/app/api/routes/users.py:update_user_me does its own sqlmodel_update + commit, while backend/app/api/routes/users.py:update_user goes through backend/app/crud.py:update_user. Duplicate-email conflicts are 409 in both, but 400 in register_user and create_user.
- Dead duplicate: backend/app/crud.py:create_item has no callers; backend/app/api/routes/items.py:create_item inlines the same Item.model_validate + commit. Ownership checks are likewise copy-pasted in read_item, update_item and delete_item in the same file.
- Redundant cascade: backend/app/api/routes/users.py:delete_user explicitly bulk-deletes Items then the User, whereas backend/app/api/routes/users.py:delete_user_me relies on backend/app/models.py:User.items (cascade_delete=True) plus FK ondelete CASCADE. Two different mechanisms for the same outcome.
- Email enumeration is only half closed: backend/app/api/routes/login.py:recover_password returns an identical message for unknown emails, but for a known email it calls backend/app/utils.py:send_email synchronously (slower response) and send_email asserts settings.emails_enabled, so with SMTP unset a registered address yields a 500 while an unknown one yields 200. Compare backend/app/api/routes/users.py:create_user, which guards with settings.emails_enabled.
- Reset tokens are stateless and replayable: backend/app/utils.py:verify_password_reset_token only checks the JWT signature/expiry (48h default); backend/app/api/routes/login.py:reset_password stores nothing to mark the token used, and changing a password (reset or update_password_me) does not invalidate previously issued access tokens (backend/app/core/security.py:create_access_token).
- A 'read' that mints credentials: backend/app/api/routes/login.py:recover_password_html_content is an HTML preview endpoint but returns a fully valid reset link for any user to any superuser; no UI uses it.
- Route guard vs validity: frontend/src/routes/_layout.tsx:Route (beforeLoad) and frontend/src/hooks/useAuth.ts:isLoggedIn only test that a token string exists in localStorage; the real validity check is the later GET /users/me via useAuth, so an expired token shows the layout briefly before the 403 handler logs out. The unused POST /login/test-token is the endpoint that was meant for this.
- Dev-only private user creation diverges from the normal path: backend/app/api/routes/private.py:create_user skips backend/app/crud.py:create_user (no duplicate-email check, no EmailStr/length validation via UserCreate) and accepts an is_verified field that backend/app/models.py:User does not have; it is mounted only when FASTAPI_ENV == 'development' in backend/app/api/main.py.
- Form default vs API default: frontend/src/components/Admin/AddUser.tsx:AddUser defaults is_active to false, while backend/app/models.py:UserBase.is_active defaults to true, so an admin who does not tick 'Is active' creates an account that cannot log in (backend/app/api/routes/login.py:login_access_token returns 'Inactive user').
- Broad cache invalidation: frontend/src/components/UserSettings/UserInformation.tsx:UserInformation, frontend/src/components/Items/DeleteItem.tsx:DeleteItem and frontend/src/components/Admin/DeleteUser.tsx:DeleteUser call queryClient.invalidateQueries() with no key, refetching every active query, while AddItem/EditItem/AddUser invalidate a specific key.

### td-1 (top-down)
- Password hashes are written in five different ways: backend/app/crud.py:create_user, backend/app/crud.py:update_user (used by reset_password and admin update_user), backend/app/api/routes/users.py:update_password_me (hashes and assigns inline, bypassing crud), backend/app/api/routes/private.py:create_user (builds User inline, bypassing crud) and backend/app/crud.py:authenticate (re-hash on login). Changing the hashing policy means touching all of them.
- A read-looking step writes: POST /login/access-token (backend/app/api/routes/login.py:login_access_token) commits User.hashed_password inside backend/app/crud.py:authenticate whenever pwdlib reports an outdated hash.
- Three different routes change a password with different rules: backend/app/api/routes/users.py:update_password_me (needs current password, rejects same password), backend/app/api/routes/login.py:reset_password (token only, no same-password check) and backend/app/api/routes/users.py:update_user (admin, any value).
- Item creation exists twice: backend/app/api/routes/items.py:create_item inlines the insert while backend/app/crud.py:create_item is only used by tests (backend/tests/utils/item.py), so tests do not exercise the route's code path.
- Account deletion works two ways: backend/app/api/routes/users.py:delete_user bulk-deletes Item rows by owner_id then deletes the user, while backend/app/api/routes/users.py:delete_user_me relies on the User.items cascade_delete / Item.owner_id ondelete CASCADE (backend/app/models.py:User, backend/app/models.py:Item). The explicit delete in delete_user is redundant or the cascade is not trusted.
- Likely UI/server mismatch that cascades: frontend/src/routes/_layout/settings.tsx:UserSettings does tabsConfig.slice(0, 3) for superusers, which is a no-op (tabsConfig has exactly 3 tabs), so superusers see Danger zone; backend/app/api/routes/users.py:delete_user_me answers them with 403; and frontend/src/main.tsx:handleApiError treats every 401/403 as an expired session, clears the token and redirects to /login. Derived from reading, not executed.
- frontend/src/main.tsx:handleApiError conflates authentication and authorization failures: backend/app/api/deps.py:get_current_user returns 403 for a bad token, but backend/app/api/deps.py:get_current_active_superuser and the 'Not enough permissions' checks in backend/app/api/routes/items.py also return 403, so any permission denial logs the user out.
- The Items page is titled 'Create and manage your items' (frontend/src/routes/_layout/items.tsx:Items) but backend/app/api/routes/items.py:read_items returns every user's items to a superuser (and duplicates the whole query in both branches).
- backend/app/api/routes/users.py:update_user_me and backend/app/api/routes/users.py:update_user both implement the 'email already taken -> 409' check inline, but only update_user then goes through backend/app/crud.py:update_user; update_user_me assigns fields directly with sqlmodel_update.
- Inconsistent email-enabled guards: backend/app/api/routes/users.py:create_user checks settings.emails_enabled before sending, but backend/app/api/routes/login.py:recover_password and backend/app/api/routes/utils.py:test_email call backend/app/utils.py:send_email directly, which asserts emails_enabled and would surface as a server error when SMTP is unconfigured (and recover_password would then leak existence of an account via 500 vs 200).
- Password reset tokens (backend/app/utils.py:generate_password_reset_token) are stateless JWTs signed with the same SECRET_KEY/HS256 as access tokens (backend/app/core/security.py:create_access_token), are valid for EMAIL_RESET_TOKEN_EXPIRE_HOURS (48) and are never invalidated after backend/app/api/routes/login.py:reset_password succeeds, so a link can be replayed until it expires.
- backend/app/api/routes/private.py:create_user accepts PrivateUserCreate.is_verified but User has no such field and the value is dropped; the endpoint also has no auth or duplicate check, relying solely on being mounted only in development (backend/app/api/main.py).
- backend/app/core/db.py:init_db re-implements the email lookup with an inline select instead of backend/app/crud.py:get_user_by_email, and backend/app/api/routes/login.py:recover_password_html_content is a superuser debug tool placed in the login router (and sets a response header named 'subject:' with a trailing colon).
- Seven of the 22 endpoints have no UI caller and are only reachable by API clients, ops tooling or tests: POST /login/test-token, GET /items/{id}, GET /users/{user_id}, POST /utils/test-email/, GET /utils/health-check/, POST /password-recovery-html-content/{email}, POST /private/users/. Logout and the route guards are purely client-side (frontend/src/hooks/useAuth.ts:useAuth, frontend/src/routes/_layout.tsx:Layout), there is no server-side session state to revoke.

### td-2 (top-down)
- A 403 means two different things and the frontend treats both as 'session expired': backend/app/api/deps.py:get_current_user returns 403 for a bad token, while backend/app/api/deps.py:get_current_active_superuser, backend/app/api/routes/items.py:read_item/update_item/delete_item and backend/app/api/routes/users.py:delete_user_me use 403 for permission denials. frontend/src/main.tsx:handleApiError wipes the token and redirects to /login on any 401/403, so a permission error logs the user out. Concretely: frontend/src/routes/_layout/settings.tsx:UserSettings meant to hide the Danger zone from superusers but tabsConfig.slice(0, 3) on a 3-tab list is a no-op, so a superuser can click Delete, get 403 from delete_user_me, and be logged out instead of seeing an error.
- User.hashed_password is written from five places with three different mechanisms: backend/app/crud.py:create_user and backend/app/crud.py:update_user (signup, admin create/edit, reset-password, bootstrap), inline in backend/app/api/routes/users.py:update_password_me, inline in backend/app/api/routes/private.py:create_user, and as a side effect of login in backend/app/crud.py:authenticate.
- Reads that write: POST /login/access-token can commit a re-hashed password via backend/app/crud.py:authenticate when pwdlib reports the stored hash needs upgrading.
- Two ways to update a user: backend/app/api/routes/users.py:update_user_me applies sqlmodel_update inline, while backend/app/api/routes/users.py:update_user goes through backend/app/crud.py:update_user. Three ways to create one: backend/app/crud.py:create_user (signup, admin, bootstrap) vs backend/app/api/routes/private.py:create_user, which skips the duplicate-email check and drops its own is_verified field.
- Two cascade strategies for removing a user's items: backend/app/api/routes/users.py:delete_user bulk-deletes Item rows explicitly, while backend/app/api/routes/users.py:delete_user_me relies on the ORM/FK cascade declared on backend/app/models.py:User.
- backend/app/crud.py:create_item duplicates what backend/app/api/routes/items.py:create_item does inline and is only used by backend tests; in effect it is test scaffolding living in production crud.
- The anti-enumeration promise in backend/app/api/routes/login.py:recover_password depends on email config: backend/app/utils.py:send_email asserts settings.emails_enabled, and unlike backend/app/api/routes/users.py:create_user the recovery handler never checks it, so a registered email returns 500 and an unknown one returns 200 when SMTP is unset.
- Authorization is spread out: the owner-or-superuser check is copy-pasted three times in backend/app/api/routes/items.py (read_item, update_item, delete_item); read_items has two near-identical query branches; the superuser gate is a dependency (backend/app/api/deps.py:get_current_active_superuser) on some routes but inline on backend/app/api/routes/users.py:read_user_by_id.
- All tokens are stateless JWTs signed with the same SECRET_KEY/HS256 and no type or audience claim: access tokens (backend/app/core/security.py:create_access_token, sub=user id) and reset tokens (backend/app/utils.py:generate_password_reset_token, sub=email) are told apart only by what sub happens to contain. Logout is client-only and reset tokens are never consumed, so both stay valid until expiry.
- Email is sent synchronously inside request handlers (backend/app/api/routes/users.py:create_user, backend/app/api/routes/login.py:recover_password, backend/app/api/routes/utils.py:test_email) with no BackgroundTasks, so SMTP latency or failure lands on the user's request.
- Admin onboarding works against itself: frontend/src/components/Admin/AddUser.tsx:AddUser defaults is_active to false (backend default is True), while backend/app/utils.py:generate_new_account_email puts the plaintext password in the welcome email, so by default users get credentials they cannot use yet.
- Lists are silently capped at 100: frontend/src/routes/_layout/items.tsx:getItemsQueryOptions and frontend/src/routes/_layout/admin.tsx:getUsersQueryOptions always fetch skip=0&limit=100 and page client-side in DataTable, so the server's skip/limit pagination is never used.
- GET /users/me is fetched through two channels: the shared ['currentUser'] query in frontend/src/hooks/useAuth.ts:useAuth (used by sidebar, dashboard, settings and every admin table row via UserActionsMenu) and a direct uncached UsersService.readUserMe call in the admin route guard frontend/src/routes/_layout/admin.tsx:Route.
- Several generated client methods have no caller in the app (testToken, readItem, readUserById, testEmail, recoverPasswordHtmlContent, healthCheck); their endpoints are reached only from tests, Swagger or infrastructure.
