## Item titles are capped at 100 characters, on input and also on read, so existing items with longer titles can no longer be shown

**Lands on:** no map step directly (lens: 0 steps touched; the only change is in the shared model `ItemBase`, which is off-map) · by reach: manage-items → opens Items page, adds a new item, edits an item, API client fetches a single item (these are the only steps whose behaviour actually changes)
**New on the map:** no new step. `backend/app/models.py:ItemBase` is off-map, but it is the validation and serialization contract for every manage-items step, so it is a map gap (it belongs as an anchor under manage-items).

### Before → after
- manage-items → adds a new item (`POST /items/`): titles of 1–255 chars accepted → titles of 101–255 chars now get a 422, because `ItemCreate` inherits the cap. The `AddItem.tsx` zod schema still has only `.min(1)`, so the user finds out only when they submit.
- manage-items → edits an item (`PUT /items/{id}`): `ItemUpdate.title` is unchanged (still `max_length=255`), so a 101–255 char title passes validation and is committed. The response (`response_model=ItemPublic`, which inherits the 100 cap) then fails, so the user gets a 500 after the write has already happened.
- manage-items → opens Items page (`GET /items/`): a stored title over 100 chars → `ItemPublic.model_validate(item)` raises → the whole list returns 500 for that item's owner, and for any superuser whose page includes it. I checked this against the head models: an `Item` with a 150-char title fails `ItemPublic.model_validate` with `string_too_long`.
- manage-items → API client fetches a single item (`GET /items/{id}`): same failure, a 500 for any item with a long title.
- manage-items → deletes an item: no change (it returns `Message` and never serializes the item).
- Schema: `Item` (table=True) also inherits `ItemBase`, so the ORM metadata now declares `item.title VARCHAR(100)`, but the database is `VARCHAR(255)` (migration `9c0a54914c78`). The PR adds no migration. Alembic `env.py` sets `compare_type=True`, so the next `--autogenerate` will emit `ALTER COLUMN title TYPE VARCHAR(100)`. Postgres rejects that if any row is longer, which would fail the operate-deployment → prestart step.

### Shape
- A one-token change (255 → 100) with a behaviour change much larger than the diff. `ItemBase` is shared by `ItemCreate`, the `Item` table and the `ItemPublic` response, so what looks like an input rule is in fact a change to stored data and to the response contract. The busyness is accidental, not essential: the stated intent ("fit the new card layout") is about display, and no card layout is in this PR (no frontend file changed; items still render through the `columns.tsx` table).
- Blast radius: lens shows `ItemBase` reachable from 17 endpoints in 6 flows, none anchored, and `models.py` is imported by 9 files. Only the four manage-items steps above really change. The administer-users, sign-in, sign-up, recover-forgotten-password and manage-own-account hits come through the `User.items` relationship and never serialize items through `ItemPublic`, so the lens over-reports them.
- Tests: none changed. The item tests use "Foo", "Updated title" and 32-char random titles, so the suite stays green and manage-items keeps its "tested" evidence. Nothing tests the 100/255 boundary, a long title already stored, or the mismatch between create and update.

### Questions to ask
1. **Reversibility / State (manage-items → opens Items page):** production `item.title` is `VARCHAR(255)`, and `ItemPublic` now rejects anything over 100 chars on read. Have you run `SELECT count(*) FROM item WHERE length(title) > 100` against production? If any rows come back, `GET /items/` returns 500 for their owners and for admins. What is the plan for those rows: truncate them in a migration, or keep the cap off the read model?
2. **Blast radius (manage-items → edits an item):** `ItemUpdate.title` still allows 255. Was that intentional? As written, a PUT with a 150-char title commits, then returns 500, and that user's Items page stays broken from then on. Which limit is the real one?
3. **Altitude:** the reason given is a card layout that isn't in this PR. Why put the cap on `ItemBase`, which covers storage, the read contract and the write contract, instead of truncating or ellipsizing in the card component, or capping only the `ItemCreate`/`ItemUpdate` inputs?
4. **State (operate-deployment → prestart migrations):** the ORM now declares `VARCHAR(100)` with no Alembic migration. Is a migration coming? If so, how will it handle existing longer titles, given that Postgres refuses the `ALTER` and prestart would fail?
5. **User-visible (manage-items → adds a new item):** existing API clients that send 101–255 char titles now get a 422, and the `AddItem`/`EditItem` zod schemas have no `.max(100)`. Should the frontend enforce the same limit so users see a field error rather than a failed submit?

VERDICT: do-not-merge
