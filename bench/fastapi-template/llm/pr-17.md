## Signed-in users can ask the API how many items they own (no UI uses it yet)

**Lands on:** nothing on the map (lens: 0 steps touched in 0 flows). It sits next to manage-items → user-views-items: same `Item` table, same owner filter as that step's count.
**New on the map:** `GET /items/count` → `backend/app/api/routes/items.py:count_items`. Step I'd add: manage-items → "API client counts its own items" (actor: external). It becomes a user step only when the dashboard badge that the commit message mentions exists.

### Before → after
- `GET /items/count`: before, this fell through to `read_item` and returned a 422 `uuid_parsing` error. After, it returns 200 with a bare integer: the number of items whose `owner_id` is the caller. For superusers too, it counts only their own items.
- manage-items → user-views-items, user-edits-item, user-deletes-item: no change. `read_items` was not edited. `PUT` and `DELETE /items/count` still return 422, because `/{id}` fully matches those methods. I checked this with a minimal FastAPI app that uses the same route order.
- Dashboard (`frontend/src/routes/_layout/index.tsx`): no change. The PR has no badge and no frontend code. The intent ("for the dashboard badge") is only half delivered.

### Shape
- Size matches intent: 11 lines for one read-only endpoint. The busiest part, the count query, copies `read_items`' non-superuser count statement word for word. That duplication is accidental but minor.
- Blast radius: no shared node was edited. Reach diff: one edge added (`count_items` → `models.Item`), and no existing code became newly reachable or unreachable. The route order matters: `/count` has to stay above `/{id}`, or it starts returning 422 again.
- Tests: none changed. `backend/tests/api/routes/test_items.py` has no count test, so the new step would enter the map as untested. The generated client in `frontend/src/client` was not regenerated. The pre-commit hook `generate-frontend-sdk` will push that to the PR in CI.

### Questions to ask
1. **Superuser semantics (user-views-items):** `read_items` gives a superuser a global `count`, but `count_items` filters on `owner_id == current_user.id` for everyone. On an admin's dashboard the badge will not match the Items page total. Which number do you want? If it's "own items only", can a test and the docstring say so?
2. **Alternatives:** `GET /items/?limit=0` already returns `{data: [], count: N}`, with the same owner filter and the superuser branch. Why add a new endpoint instead of having the badge call that?
3. **Contract / reversibility:** the response is a bare JSON integer, while every other items endpoint returns an object. Once the badge or outside clients depend on it, you can't add fields (such as per-status counts) without breaking them. Should it be `{"count": n}` now, while nothing consumes it?
4. **Tests:** can you add three tests to `test_items.py`? (a) A normal user's count leaves out another user's items. (b) `GET /items/count` returns 200, not 422, which guards the route order against `/{id}`. (c) Superuser behaviour, whichever way Q1 is decided.
5. **Failure / load, when the badge lands:** the dashboard is the landing page after login. Each load would run a `count(*)` filtered on `item.owner_id`, and no Alembic migration indexes that column. If the call fails, does the badge hide or show "0"?

After: this adds a step to manage-items. Once it merges (and again when the badge ships), re-run the map loop in `docs/flowmap/README.md` rather than editing `map.json` by hand.
