## Reading, editing and deleting a single item now share one ownership check; users and API clients see no difference

**Lands on:** manage-items → api-client-reads-item (`GET /items/{id}`), user-edits-item (`PUT /items/{id}`), user-deletes-item (`DELETE /items/{id}`)
**New on the map:** no new endpoints and no new step. `backend/app/api/routes/items.py:get_owned_item` is new off-map code. It is a hop inside the three steps above (load the item, return 404 or 403, hand it back), so the next map run should add it to their `code_path`.

### Before → after
- api-client-reads-item: the handler loaded the item, returned 404 "Item not found" if it was missing and 403 "Not enough permissions" if the caller was neither a superuser nor the owner → it runs the same checks in the same order with the same codes and messages, now through `get_owned_item`. The response body is unchanged.
- user-edits-item: the same inline 404/403 check ran before the partial title/description update → the same check now runs through the helper. The update logic is untouched.
- user-deletes-item: the same inline 404/403 check ran before the hard delete → the same check now runs through the helper. The delete is untouched.
- user-views-items (`GET /items/`): not touched. It still applies its own `owner_id == current_user.id` filter, with its own superuser bypass.

### Shape
- The size matches the intent. The commit says "extract the ownership check", and the diff is +12/−16 in one file. The helper's body matches the three copies it replaces line for line: the same `session.get`, the same superuser bypass, and the 404 still comes before the 403. Nothing here is busy. This is plain deduplication, and it settles the "ownership checks are copy-pasted in read_item, update_item and delete_item" note in docs/flowmap/QUESTIONS.md.
- The blast radius stays within these three steps. Reach covers only the 3 steps whose handlers changed. The reach diff shows 0 code newly reachable and 0 no longer reachable, so the check moved but no endpoint lost it. The helper has no route decorator, so OpenAPI and the generated frontend `ItemsService` stay the same. No models, migrations or stored data are touched.
- Tests: none changed, and the behaviour needs no new ones. `backend/tests/api/routes/test_items.py` already checks 404 "Item not found" and 403 "Not enough permissions" on all three endpoints, plus the superuser success path, so the helper is tested through each of its callers. All three steps keep evidence level "tested".
- Lint: `ruff format --check` (`backend/scripts/lint.sh`, pre-commit `local-ruff-format`) fails at head because it would wrap the new 90-character `def get_owned_item(...)` line. This is formatting only and has no effect at runtime.

### Questions to ask
1. **Altitude** (api-client-reads-item, user-edits-item, user-deletes-item): `get_owned_item(session: SessionDep, current_user: CurrentUser, id: uuid.UUID)` already has the signature of a FastAPI dependency, but each handler calls it by hand. Did you consider `OwnedItem = Annotated[Item, Depends(get_owned_item)]`, so a handler receives an item that has already passed the check? As written, the next single-item endpoint still has to remember to call it.
2. **Blast radius** (user-views-items, anchor `items.py:read_items`): the list endpoint keeps its own copy of the ownership rule (the `owner_id == current_user.id` filter plus the superuser bypass). Is `get_owned_item` meant to be *the* ownership rule? If so, a later change to it, such as shared items, would let the list and the single-item endpoints disagree about what a user may see. Should the list filter live next to the helper?
3. **User-visible** (user-edits-item, user-deletes-item): this PR keeps 403 for an item the caller doesn't own, which is right for a refactor. QUESTIONS.md notes that `frontend/src/main.tsx:handleApiError` signs the user out on any 403, so a refused edit or delete logs them out. That is now a one-line change in one place. Is a follow-up planned, and if so, would 404 be acceptable to existing API clients?
4. **Check** (all three steps): run `ruff format app` before merge, or the pre-commit/lint job fails on the `def get_owned_item` line.
