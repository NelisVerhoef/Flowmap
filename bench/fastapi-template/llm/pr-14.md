## Items get a hidden `priority` number (always 0), but the migration fails on any database that already has items

**Lands on:** manage-items → User opens the Items page and sees their items, User adds a new item with a title and description, User edits an item's title or description, User deletes an item after confirming, An API client fetches a single item by id · administer-users → Admin deletes a user together with all of their items
**New on the map:** no endpoints. The lens lists the new Alembic revision `7c1e2d3f4a5b_add_priority_to_item.py` (`upgrade`/`downgrade`) as off-map. It is not a new step: it runs inside operate-deployment → "Prestart script applies migrations and creates the first superuser if missing" (and sign-up → "Container prestart runs migrations…"). Those steps have no endpoint, so the lens can't anchor migrations to them. That is a gap in the map, not a step to add, so there's no need to re-run the map loop for this PR.

### Before → after
- Prestart (`alembic upgrade head`, the "Prepare database" step in both deploy workflows): did nothing on an up-to-date DB → now runs `ALTER TABLE item ADD COLUMN priority INTEGER NOT NULL` with **no server default**. This works on an empty `item` table. On any table with rows, Postgres rejects it with `column "priority" of relation "item" contains null values` (I reproduced this on Postgres 16, and adding `DEFAULT 0` makes it succeed). `prestart.sh` runs with `set -e`, so the deploy stops there. Because Alembic runs this migration in a transaction, the failed upgrade rolls back cleanly.
- User adds a new item (`POST /items/`): the row had no priority → the row gets `priority = 0`. This default lives only in the ORM model (`Field(default=0)`). `ItemCreate` has no such field, so clients can't set it.
- Items page / fetch one item / edit item / delete item: nothing changes for users. `ItemPublic` and `ItemUpdate` don't expose `priority`, so responses and the generated frontend client stay the same. The ORM's SELECT now includes `item.priority`, which only matters if this code runs against a schema that hasn't been migrated.
- Admin deletes a user: unchanged (it still bulk-deletes with `DELETE FROM item WHERE owner_id = …`).

### Shape
- The size matches the intent. "Add a priority column" is one model line plus a 23-line migration, and that is all the PR does: no API, UI or sort order uses the column. The migration is the busiest part, and its single line is where the defect is. The model says `default=0` but the migration has no `server_default`, so existing rows get no value. The previous migration on the same table (`fe56fa70289e`, adding created_at) used `nullable=True` so existing rows would survive. This PR drops that precaution.
- Blast radius: Reach says `Item` can be reached from 17 endpoints in 6 flows, 11 of them unanchored (sign-in, password recovery, admin user CRUD, …). Most of that comes through the lazy `User.items` relationship and overstates the risk. The code that actually reads the `item` table is the 5 manage-items steps, admin user delete, and self-delete (`DELETE /users/me`, where the ORM cascade loads the user's items). None of these behave differently once the migration has applied.
- Tests: none changed. All 6 touched steps stay at "tested", but those tests can't catch this. `test-backend.yml` runs `docker compose down -v` and migrates an empty DB, so CI will pass while the production migration fails. No test checks the new default or runs a migration over existing rows.

### Questions to ask
1. **Failure (operate-deployment → Prestart applies migrations):** `upgrade()` adds `priority` as `NOT NULL` with no `server_default`. Production's `item` table has rows, so `alembic upgrade head` will fail with a NotNullViolation and every deploy from this commit on will stop at "Prepare database". Did you run this upgrade against a copy of real data? Would you add `server_default="0"` to the migration (and `sa_column_kwargs={"server_default": "0"}` on the model so autogenerate agrees), or split it into three steps: add as nullable → backfill → set NOT NULL?
2. **Failure (operate-deployment, docker-compose deploy):** `docker compose build` re-tags `backend:latest` before prestart runs. If prestart fails and someone later runs `docker compose up -d`, the new code starts against a schema with no `priority` column. Every Items-page, get, edit and delete query, plus self-delete, would then return 500 (`column item.priority does not exist`). Does anything stop the new image from starting after a failed migration?
3. **State (manage-items, who reads it?):** Nothing reads or writes `priority`: not the API schemas (`ItemPublic`/`ItemCreate`/`ItemUpdate`), not the list ordering in `read_items` (`created_at desc`), not the frontend. What follow-up will use it, and why land the column first? What does the value mean (is 0 "none"? does higher mean more urgent? what's the range?), and does it need a DB-level check now, before clients can write to it?
4. **Reversibility:** `downgrade()` drops the column. That's harmless while every value is 0, but once the follow-up lets users set priorities, rolling back this revision deletes them. Is that acceptable, or should the downgrade be blocked once the column has non-default values?
5. **Map gap (operate-deployment → Prestart):** The lens shows schema migrations as "off-map" because the prestart steps have no endpoint. Should that step anchor `backend/app/alembic/versions/*` so the next schema change lands on the deploy flow, where this risk actually sits?

VERDICT: do-not-merge
