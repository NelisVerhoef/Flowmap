## Every deployment, production included, now serves the dev-only "create a user" test endpoint (`POST /api/v1/private/users/`) with no auth

**Lands on:** sign-up → "Test harness creates a user through the development-only private API" (`test-harness-seeds-user`, `POST /private/users/`)
**New on the map:** no new code, but the step gets a new actor. `POST /private/users/` goes from "external test harness, dev only" to "anyone who can reach the prod host". If this merges, it is an unauthenticated sign-up path next to `POST /users/signup`, and the step's name ("development-only") is false.

### Before → after
- sign-up / test-harness-seeds-user: `private.router` was mounted only when `FASTAPI_ENV == "development"`. That variable is set by `.env`, `compose.override.yml`, `backend/scripts/test.sh` and `scripts/generate-client.sh`. Production `compose.yml` does not set it. → Now it is mounted unconditionally. Prod serves `POST /api/v1/private/users/` (Traefik routes on `Host` only, with no path filter) and lists it in the prod `/api/v1/openapi.json` and `/docs`.
- What that now-public endpoint does (`private.py:create_user`, code unchanged):
  - no auth dependency;
  - `email: str`, not `EmailStr`;
  - no password or `full_name` length limits;
  - no duplicate-email check;
  - builds `User(...)` inline, skipping `crud.create_user`;
  - silently drops `is_verified`.

  Next to the already-open `/users/signup`, it is open registration without any of the validation.

### Shape
- **Intent vs size:** the commit says "simplify router registration", which reads as a refactor. The diff is +1/-5 and does not preserve behaviour: the deleted `if` was the only guard on an unauthenticated write endpoint. All the busyness is in that deletion, and it is accidental. The "simplification" *is* the behaviour change. Dropping the `settings` import is cosmetic.
- **Blast radius:** the new prod surface writes `User`, which several paths read:
  - login (`crud.authenticate`);
  - `GET /users/` (admin list, which calls `UserPublic.model_validate` per row);
  - `GET /users/me`;
  - admin edit and delete.

  A row whose `email` is not a valid email should fail `UserPublic` (`EmailStr`) validation on those reads. One such row could make the admin user list return 500 for every admin. A duplicate email hits the unique index and returns 500, not 400.
- **Tests:** none changed. `backend/tests/api/routes/test_private.py` runs under `FASTAPI_ENV=development` (test.sh), so it passes both before and after. Nothing checks that the route is absent outside development, so CI cannot catch this. The step's evidence stays "tested", but only for dev mode.

### Questions to ask
1. **Blast radius / altitude** (`api/main.py` → test-harness-seeds-user): did you mean to expose `POST /api/v1/private/users/` in production? Removing `if settings.FASTAPI_ENV == "development"` mounts an unauthenticated user-creation endpoint on every deploy. If the goal was only to drop the conditional, what gates the router now? Options: a `get_current_active_superuser` dependency, a test-only include in `conftest.py`, or registering it from a dev-only entrypoint.
2. **State** (`User` table): `private.create_user` skips `EmailStr` and length validation and the duplicate check. If someone POSTs `{"email": "x", "password": "a", "full_name": "..."}` to prod, does `GET /users/` (and the admin page) return 500 for every admin until someone deletes that row by hand? And can that 1-character-password account log in?
3. **Alternatives:** what does the Playwright helper (`frontend/tests/utils/privateApi.ts:createUser`) need that `POST /users/signup`, or superuser `POST /users/`, cannot give it? If the private endpoint has to stay, why not keep the env gate *and* require a superuser?
4. **Failure / tests:** which test fails if this route leaks into a non-development environment? `test_private.py` only runs with `FASTAPI_ENV=development`. Could you add one that builds the app with `FASTAPI_ENV` unset and expects 404 on `/private/users/`?
5. **Reversibility:** if this ships and is then reverted, users created through it stay in `User`, possibly with invalid emails or trivial passwords. No column marks them apart from signup users. How would we find and clean them up?
