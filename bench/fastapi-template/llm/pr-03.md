### Before → after
- admin-edits-user (`PATCH /users/{id}`, writes `User.is_active`): unticking "Active" cut the user off on their next request → it only blocks their next *login*. Sessions already open keep working until the JWT expires (`ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*8`, with no revocation)
- sign-in → app-loads-current-user (`GET /users/me`), api-client-checks-token (`POST /login/test-token`): an inactive user's token got 400 "Inactive user" → 200 with the user object (`is_active: false`)
- manage-items (5 steps), manage-own-account (3 steps): an inactive user was refused → can read, create, edit and delete items, change email and password, and delete the account
- administer-users, admin-sends-test-email, admin-previews-recovery-email: a deactivated superuser was refused → `get_current_active_superuser` checks only `is_superuser`, so they keep full admin power and can `PATCH /users/{own_id} {"is_active": true}` to undo their own deactivation
- Unchanged: `POST /login/access-token` and `POST /reset-password/` still refuse inactive users. Deleted users are still cut off at once (404), so deleting now revokes access and deactivating does not

### Questions to ask
1. **Blast radius / State (admin-edits-user → every `CurrentUser` step):** login only issues tokens. Tokens last 8 days and can't be revoked. With this check gone, what stops a user an admin deactivates today from calling `GET /items/`, `PATCH /users/me`, `DELETE /users/me` and the rest until their token expires? Is "deactivate" now meant to mean "can't log in again"?
2. **Blast radius (administer-users):** a deactivated superuser with a live token can call `PATCH /users/{own_id}` with `is_active: true` and re-enable themselves, then log in for a fresh token. Was it intended that an admin can undo their own deactivation?
3. **State / Reversibility (production data):** on deploy, any existing `is_active=false` user holding a token from the last 8 days gets access back immediately. Have you checked how many inactive accounts exist in production and when they were deactivated? Rolling back restores the check (no data is written), but anything they do in the meantime stays.
4. **Alternatives:** what problem was this check causing? If it was the 400: `main.tsx` logs out only on 401/403, so inactive users saw error toasts instead of being sent to login. Returning 403 here would fix that and keep revocation. The check reads a field on a row already loaded, so it adds no query cost.
5. **Tests (sign-in → app-loads-current-user):** which outcome should `GET /users/me` give for a valid token whose user has `is_active=false`, 200 or 4xx? Please pin it with a test either way, and add one for login's "Inactive user" branch, which this PR now relies on alone.
