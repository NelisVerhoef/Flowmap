## Admin "delete user" now leaves item removal to the User→Item cascade instead of its own bulk delete. The admin sees the same result.

**Lands on:** administer-users → Admin deletes a user together with all of their items
**New on the map:** nothing. No endpoint or step was added. Item is still written on this step, but now through `User.items` instead of a direct statement (lens: the edge `users.delete_user → models.Item` was removed).

### Before → after
- Admin deletes a user (`DELETE /users/{user_id}`):
  - **Before:** one bulk `DELETE FROM item WHERE owner_id=…`, then `session.delete(user)` (its `items` collection was already empty).
  - **After:** `session.delete(user)` alone. `User.items` has `cascade_delete=True`, which SQLModel 0.0.39 turns into `cascade="all, delete-orphan"` with `passive_deletes` left False. So the ORM loads every item the user owns, deletes them one row at a time, then deletes the user. The FK `ondelete="CASCADE"` (migration 1a31ce608336) is a backstop.
  - **Unchanged:** the response body, the 404 and self-delete 403 guards, and the superuser dependency. This is the mechanism `DELETE /users/me` already uses.

### Shape
- **Intent vs size:** 5 lines change (1 added, 4 removed) to remove one behaviour, so size matches intent. Nothing is busy. It settles the "two cascade strategies" finding that docs/flowmap/QUESTIONS.md raises four times (delete_user vs delete_user_me).
- **Blast radius:** none beyond this step. Lens Reach shows 1 endpoint, 1 flow and 0 hidden steps. Reach diff shows 0 code newly reachable and 0 code no longer reachable. No auth or validation check moved.
- **Production:**
  - No schema or data change.
  - The FK cascade is an ancestor of migration head fe56fa70289e, which `scripts/prestart.sh` applies with `alembic upgrade head`.
  - The ORM cascade deletes the items even on a database where that FK were missing.
  - Clients get an identical response.
  - Rollback is a plain revert, and no stored state depends on the change.
- **Tests:** none changed, and the step stays "tested". But that evidence only covers the user row: `test_delete_user_super_user` (and `test_delete_user_me`) create a user with no items and never check items. The "together with all of their items" part of the step was unasserted before and still is.

### Questions to ask
1. **Mechanism (Altitude):** the commit says "rely on ON DELETE CASCADE", but with `passive_deletes` False the database cascade never fires. Instead `session.delete(user)` loads all of the user's Item rows into the request and issues one DELETE per item. Did you mean Postgres to do it (`passive_deletes=True`/`"all"` on `User.items`)? Or is per-row ORM deletion acceptable for a user with tens of thousands of items, where the admin's request could time out and roll back?
2. **Test the promise:** the admin dialog (`Admin/DeleteUser.tsx`) tells the admin that all of the user's items "will also be permanently deleted". Can `test_delete_user_super_user` and `test_delete_user_me` create an item first and assert that `select(Item).where(Item.owner_id == user_id)` comes back empty? Today nothing would catch someone dropping `cascade_delete` from `User.items`.
3. **State / DB parity:** is every deployed database (prod, staging, restored backups) past migration 1a31ce608336? It doesn't matter today because the ORM cascade does the work. If question 1 leads to `passive_deletes`, a database without that FK would turn every admin user-delete into a 500 (FK violation) instead of removing the items.
4. **Map:** this makes delete_user and delete_user_me use the same mechanism. Should the map loop be re-run to clear the four "two cascade strategies" entries in QUESTIONS.md? No step moved, so `map.json` itself needs no change.

VERDICT: safe-to-merge
