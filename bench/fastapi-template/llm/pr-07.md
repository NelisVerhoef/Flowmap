## Sign-up now lets any visitor pick their own role: a public request with `"is_superuser": true` creates an admin account

**Lands on:** sign-in → Visitor signs up with full name, email and password (`POST /users/signup`). Lens reports 0 anchored steps touched; this step is reached through `UserRegister` and is not anchored on the map. Downstream, the change affects every step gated on `User.is_superuser`: administer-users → admin-lists-users, admin-creates-user, admin-edits-user, admin-deletes-user, admin-looks-up-user · manage-items (superusers see and edit every item) · operate-deployment → admin-sends-test-email · recover-forgotten-password → admin-previews-recovery-email
**New on the map:** no new steps. `backend/app/models.py:UserRegister` should be a hop on `visitor-registers-account`. The step's code_path does not list the request model, and lists `UserCreate` only as disputed.

### Before → after
- visitor-registers-account: the request body accepted `email`, `password` and `full_name`. Pydantic's default `extra="ignore"` dropped anything else, so every signup stored `is_superuser=False, is_active=True` → the body now also accepts `is_superuser` and `is_active`. `register_user` passes them through `UserCreate.model_validate(user_in)` → `crud.create_user` → `User`. As a result, an unauthenticated caller can store `is_superuser=True` (or `is_active=False`). I checked this by running the base and head `models.py` through the same validate chain with `{"is_superuser": true}`: base stores False, head stores True.
- Sign-up form in the shipped frontend (`useAuth` sends only the 3 fields): unchanged, because the defaults are still False/True.
- OpenAPI `UserRegister` schema: goes from 3 properties to 5 (adds optional `is_active` and `is_superuser`). `frontend/src/client/types.gen.ts` was not regenerated, so the client and the API contract drift apart.

### Shape
- Intent vs size: the commit says "reuse UserBase fields for registration", a 2-line dedup refactor. The behaviour change is much larger than the code change. `UserRegister` was a separate, narrow `SQLModel` that served as the allow-list for the only unauthenticated write endpoint. `UserBase` is the shared shape behind the admin-only `UserCreate` and the `User` table, so inheriting from it brings admin-only fields into a public input. The duplication being removed (`email`, `full_name`) was accidental and cheap. Removing it costs the endpoint its security boundary.
- Blast radius: `models.py` is imported by 9 files, but the edit is confined to `UserRegister`, whose only caller is `register_user`. The field it opens up is the system's single authorization bit. That bit is checked by `deps.get_current_active_superuser` on 7 routes and inline in `items.py` (4 places) and `users.py` (2 places). Lens's Reach diff shows nothing "no longer reachable" because no call edge was removed. The check that was lost is a schema allow-list, which the call graph cannot see.
- Tests: no test files changed. `test_register_user` posts only email, password and full_name, so it still passes. No test asserts that signup ignores `is_superuser` or `is_active`. The step's evidence level stays "contested".

### Questions to ask
1. **Blast radius (visitor-registers-account → administer-users):** At pr-07, an unauthenticated `POST /users/signup` with `{"email": ..., "password": ..., "is_superuser": true}` stores a superuser. That account then passes `get_current_active_superuser` for listing, creating, editing and deleting any user, and can read and edit everyone's items. Did you mean for signup to accept these fields? If the goal is only to share `email` and `full_name`, can `UserRegister` inherit from a small base that holds just those two fields, or explicitly exclude or pin `is_superuser` and `is_active`, instead of inheriting from `UserBase`?
2. **State / reversibility:** If this build has run anywhere with signup open, how would we find accounts that `/users/signup` created with `is_superuser=True` or `is_active=False`? Nothing records how a user was created. Rolling back the code will not demote those accounts.
3. **Tests (sign-in → visitor-registers-account):** Can you add a case to `backend/tests/api/routes/test_users.py` that posts `is_superuser: true` and `is_active: false` to `/users/signup`? It should assert that the stored user is an active non-superuser. That test would have caught this change and would protect the next edit to `UserBase`.
4. **Map gap / contract:** The OpenAPI `UserRegister` schema gains two fields, but the generated client was not updated. Was any API contract change intended? Should `models.py:UserRegister` be anchored on `visitor-registers-account`, so that the next edit to it shows up as touching sign-up rather than as off-map?
