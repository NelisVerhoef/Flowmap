## Rewrites the API descriptions of three user endpoints (list users, edit own profile, delete user). Nothing users do or see in the app changes.

**Lands on:** administer-users → Superuser opens the Admin page and sees all users, Admin deletes a user together with all of their items · manage-own-account → User edits their full name or email on the My profile tab
**New on the map:** none. No new endpoints and no off-map code. The lens found no Reach diff: the call graph is the same at base and head.

### Before → after
- Superuser opens the Admin page and sees all users (`GET /users/`): OpenAPI description "Retrieve users." → "Retrieve users, newest first. Superusers only." The query, ordering (`created_at desc`), superuser guard and response are unchanged.
- User edits their full name or email (`PATCH /users/me`): "Update own user." → "Update the signed-in user's own name or email." The handler is unchanged and `UserUpdateMe` still allows only `full_name` and `email`, so the new text is accurate.
- Admin deletes a user with all their items (`DELETE /users/{user_id}`): "Delete a user." → "Delete a user and everything they own. Superusers only." The handler is unchanged. It still bulk-deletes `Item` rows by `owner_id`, then the user, and `Item` is the only table with an `owner_id` today.

### Shape
- Intent vs size: the commit says "clearer endpoint docstrings" and the diff is exactly 3 docstring lines in `backend/app/api/routes/users.py`. The amount of code matches the change. Nothing is busy. Paths, parameters, schemas, status codes, data and DB access are all unchanged. The only output that differs is the `description` field in `/openapi.json`.
- Blast radius: no shared node was touched. Each changed symbol is reachable from its own single endpoint (1 endpoint, 1 flow each).
- Tests: none changed and none needed for runtime behaviour. Evidence levels did not move: `GET /users/` is still *contested* and the other two are still *tested*. One side effect: `frontend/src/client/sdk.gen.ts` still has the old JSDoc ("Retrieve users." / "Update own user." / "Delete a user."). The `generate-frontend-sdk` pre-commit hook will regenerate it, so the first CI pre-commit run will fail and then push an auto-format commit to this PR.

### Questions to ask
1. **`GET /users/` "newest first"**: the docstring now puts this ordering in the public API docs, but migration `fe56fa70289e` added `user.created_at` as nullable with no backfill. On Postgres, `ORDER BY created_at DESC` puts NULLs first, so on any deployment older than that migration the *oldest* users come first. There is also no tie-breaker, so `skip`/`limit` pages can shift. Should we backfill or add `nulls_last()` plus an `id` tie-breaker, or should the docstring not promise an order? (This is existing behaviour; the PR only documents it.)
2. **`DELETE /users/{user_id}` "everything they own"**: this is true today only because `Item` is the sole owned table and the handler deletes it explicitly (on top of `cascade_delete` on `User.items`). The map step says "all of their items". If someone adds another owned table, the published description becomes false without anyone noticing. Should the text say "and all of their items", or should a test pin "deletes everything owned"?
3. **Generated client drift**: do you want to run `scripts/generate-client.sh` and commit the updated `frontend/src/client/sdk.gen.ts` in this PR, so pre-commit passes on the first run instead of relying on the bot's push? Fork PRs go through the `lite-action` path instead.
4. **Any consumers of the OpenAPI descriptions?** Do external API clients or doc sites snapshot or diff `/openapi.json`, so that a description-only change would trigger a "contract changed" alert? If not, this is purely cosmetic.
