## Password-reset links now stay valid for 14 days instead of 48 hours, and the email now says "336 hours"

**Lands on:** the lens reports no map steps. It lists one off-map change: `backend/app/core/config.py` → `Settings` (imported by 9 files); the only change is `EMAIL_RESET_TOKEN_EXPIRE_HOURS: 48 → 24 * 14`. *Map/call-graph gap (my reading, separate from the lens):* the constant is read as an attribute, not called, so the graph can't see who uses it. Two functions read it: `backend/app/utils.py:generate_password_reset_token` (the JWT `exp`) and `backend/app/utils.py:generate_reset_password_email` (`valid_hours`). So the change really lands on **recover-forgotten-password → steps 1, 2, 3**.
**New on the map:** nothing.

### Before → after
- recover-forgotten-password #1 `POST /password-recovery/{email}`: mails a link that expires after 48 h, and the email says "This link will expire in 48 hours." → mails a link that expires after 336 h, and the email says "This link will expire in 336 hours."
- recover-forgotten-password #2 `POST /reset-password/`: accepts a reset token up to 48 h old → accepts one up to 14 days old. Tokens issued before the deploy keep their 48 h `exp`, which is baked into the JWT.
- recover-forgotten-password #3 `POST /password-recovery-html-content/{email}` (admin): the preview says "336 hours" and creates a 14-day token.

### Shape
- Size matches the mechanics (one constant), but **the stated intent doesn't match the repo**. The commit says "the email says the link is valid for two weeks". The only reset email (`backend/app/email-templates/reset_password.html`, built from `packages/react-email/emails/reset_password.tsx`, both unchanged) renders `{{ valid_hours }}` from this same setting, and no "two weeks" text exists anywhere in the repo. The copy already followed the number, so there was no mismatch to fix. What does change is a security parameter.
- Security radius, for every existing user: reset tokens are stateless HS256 JWTs signed with `SECRET_KEY`, and they travel in a URL query string (`/reset-password?token=…`). They are also never invalidated after `login.py:reset_password` succeeds (already flagged in `docs/flowmap/QUESTIONS.md`). So a leaked, forwarded or already-used link can reset the password again for 14 days instead of 2, a 7× longer window. Neither `.env` nor the compose files override the value, so the new default goes to production.
- Reversibility: a revert does not shorten tokens created while this was live; they stay valid for their full 14 days. The only way to kill them early is rotating `SECRET_KEY`, which also logs out every user because access tokens share that key.
- Tests: none changed, and no test covers reset-token expiry (`test_login.py` only uses fresh tokens). Steps 1–2 stay "tested" only on the happy path, so nothing would catch either value.

### Questions to ask
1. **Which email says "two weeks"?** In this repo, `reset_password.html` prints `valid_hours` from the setting you changed: it says "48 hours" today and would say "336 hours" after this PR. If production uses a different template, or a help-centre/support page promises two weeks, please point to it. Otherwise the reason for the change doesn't hold. (step 1, `generate_reset_password_email`)
2. Was the security trade-off meant to be part of this? Reset tokens are not single-use, because `reset_password` never invalidates them. A used or leaked link can take over the account for 14 days instead of 48 h. If a longer lifetime is really the product decision, should it come with single-use tokens (e.g. a claim tied to the password hash or a `password_changed_at`), plus a security sign-off? (step 2, `verify_password_reset_token`)
3. If the goal is only consistent wording, why change the token lifetime instead of the copy? For example, render days in the template, or fix whichever external text says two weeks. Is "This link will expire in 336 hours." the copy you want users to see? (steps 1 and 3)
4. Rollback: tokens created under the 336 h setting survive a revert. Is that acceptable, or is the plan to rotate `SECRET_KEY` and log everyone out? (step 2, Reversibility)
