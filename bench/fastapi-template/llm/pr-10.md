## Passwords are hashed and checked with bcrypt only. Every existing user with an Argon2 hash can no longer log in.

**Lands on:** lens: no map steps (0 steps, 0 flows). Both changed symbols are module-level objects (`security.password_hash`, `crud.DUMMY_HASH`), not functions, so the call graph does not link them to any step. *Map gap, stated separately:* by behaviour, the change reaches every step that calls `verify_password`/`get_password_hash`: sign-in → 1 signup, 2 log in · manage-own-account → 2 change password · administer-users → 2 create, 3 edit · recover-forgotten-password → 2 set new password · operate-deployment → 2 first superuser · sign-up → 2 private create
**New on the map:** nothing. This swaps the hasher inside existing steps.

### Before → after
- sign-in → 2 log in (`POST /login/access-token`): `$argon2id$` hashes verify, and `$2b$` hashes verify and are rehashed to Argon2 → `$2b$` verifies; an Argon2 hash makes `verify_and_update` raise `UnknownHashError` (no handler, so a 500 and an error toast). On main, Argon2 is the current hasher, so every user created or logged in since then has an Argon2 hash, the prestart first superuser included.
- manage-own-account → 2 change password (`PATCH /users/me/password`): the current-password check on an Argon2 hash → 500.
- signup / admin create / admin edit / reset-password / private create / prestart superuser: new hashes `$argon2id$…` → `$2b$12$…`. The locked bcrypt 5.0.0 raises `ValueError` for passwords over 72 bytes, but the models allow up to 128 (`max_length=128`), so a password of 73–128 bytes → 500.
- sign-in → 2, unknown email: the dummy check against an Argon2 hash → a bcrypt cost-12 hash (a valid 60-char `$2b$` hash). A password over 72 bytes now gives a 500 instead of a 400.
- Unchanged: recover-forgotten-password → 2 only *writes* a hash. It is the one self-service way out for locked-out users, and only if SMTP is configured.

### Shape
- Intent vs size: +3/−9 lines, a one-line hasher swap plus a new dummy hash. The code size matches "make bcrypt the default". The behaviour change is much larger: stored data stops being compatible. Nothing in the diff is busy. What's missing is the essential part: a way to verify the old hashes, or a migration for them.
- Blast radius: `password_hash` is the only hasher behind both `verify_password` and `get_password_hash`, so every password-reading and password-writing step in 6 flows goes through it. The lens shows 0 because module-level assignments aren't linked to steps, not because nothing is reached.
- Stated reason vs diff: `backend/pyproject.toml` still requires `pwdlib[argon2,bcrypt]`, and `uv.lock` (built with `uv sync --frozen` in the Dockerfile) still pins `argon2-cffi-bindings 25.1.0`, which ships manylinux/musllinux aarch64 wheels. This diff doesn't change what the ARM image installs.
- Tests: none changed. Three existing tests assert `$argon2` and should now fail: `tests/api/routes/test_login.py:129` and `:165`, `tests/crud/test_user.py:96`. sign-in → 2 and manage-own-account → 2 still say "tested", but the tests behind them would be red. No test covers the case that matters: an existing Argon2 user logs in after the switch.

### Questions to ask
1. **State / blast radius (sign-in → 2, `crud.authenticate`):** production `user.hashed_password` rows are `$argon2id$` (main hashes with Argon2, and rehashes bcrypt to Argon2 on login). With `Argon2Hasher` gone, `verify_and_update` raises `UnknownHashError` for all of them, the first superuser included, so login and change-password return 500. Why not `PasswordHash((BcryptHasher(), Argon2Hasher()))`? Argon2 would then only verify old hashes, and `verify_and_update` would rehash each user to bcrypt on their next login. If Argon2 really can't be installed, what is the migration plan for the existing hashes (forced reset email? admin reset?), and how does the superuser get back in?
2. **Alternatives (stated intent):** the ARM build still installs `argon2-cffi` (pyproject extra `argon2` and `uv.lock` are unchanged, and aarch64 wheels exist for 25.1.0). What exactly fails on ARM: a build-time install error, or an import error at runtime? If it's the install, this PR doesn't fix it. If it isn't, Argon2 can stay as the fallback in Q1.
3. **Failure (signup, change password, reset, admin create/edit):** bcrypt 5.0.0 raises `ValueError` above 72 bytes, but `UserCreate`/`UpdatePassword`/`NewPassword` accept up to 128 characters. A user who picks a long password now gets a 500 instead of an account. Will you cap passwords at 72 *bytes* in the models and the UI, or pre-hash the password before bcrypt?
4. **Failure / security (`DUMMY_HASH`, sign-in → 2):** the dummy hash exists so that "no such email" can't be told apart from "wrong password". After this change, an unknown email gets a 400 after a cost-12 bcrypt check, but a registered Argon2 user gets an instant 500. The status code and the timing both reveal which emails have accounts. Does fixing Q1 close this, and do you want a test that compares the two responses?
5. **Tests / reversibility:** the three tests that assert `$argon2` were left as they are. Did CI run on this branch? Rolling back to main after merge is safe, because main verifies both formats. The break happens only going forward, so a test like "existing Argon2 user can still log in" would have caught it. Can you add one?
