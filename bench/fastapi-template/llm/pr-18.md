## Admins get a search-by-email-prefix endpoint, but every "find user by email" in the app now returns the first user whose email *starts with* the input

**Lands on:** sign-in → Visitor signs up, User logs in · recover-forgotten-password → User enters email to receive reset link, User opens emailed link and sets new password, Admin renders recovery email HTML · administer-users → Admin creates a user, Admin edits a user · manage-own-account → User edits name/email on My profile
**New on the map:** `GET /users/search` (superuser only). I'd add it as administer-users step "Admin searches users by email prefix". No frontend calls it and the generated client was not regenerated.

### Before → after
- User logs in (`crud.authenticate`): exact email match → first row, ordered by email, matching `email LIKE '<input>%'`. `startswith` does not escape its input, so `_` and `%` act as wildcards. In byte order, `j_smith@corp.com` now resolves to `j.smith@corp.com` and fails the password check, which locks the real `j_smith` out.
- User enters email for a reset link: exact → prefix. `POST /password-recovery/admin` emails a link to whichever user sorts first under `admin…`. The JWT `sub` is the raw input (`admin`), not that user's email.
- User sets a new password via the link: the token's `sub` is resolved by prefix again when the link is used, which can be a different user from the one who received the email.
- Visitor signs up / Admin creates a user: "already exists" now fires on any prefix collision. `bob@example.co` is refused if `bob@example.com` exists, which also lets anyone check which emails are registered.
- User edits own email / Admin edits a user: 409 whenever the new email is a prefix of someone else's.
- Admin renders recovery email HTML: same prefix lookup, and the token is issued for the raw input.
- New: `GET /users/search?q=&limit=` returns up to `limit` users by email prefix. Its `count` is the page length, while `GET /users/` returns the total. `limit` has no upper bound.

### Shape
- Intent vs size: the commit says "add admin search by email", which is one new endpoint plus a query (+28/−4). The risky part is the 3-line rewrite of `get_user_by_email` so it reuses `search_users`. Nothing in the stated intent needs that rewrite (accidental, not essential), and the commit message doesn't mention it.
- Blast radius: `get_user_by_email` is reachable from 8 endpoints in 4 flows. Reach diff shows the new edge `get_user_by_email → search_users`, so every auth path now runs prefix plus wildcard semantics. It is also slower: `=` used the unique email index, but `LIKE 'x%'` under a non-C collation (the postgres:18 image defaults to en_US.utf8) cannot use a plain btree index, so login, signup and reset do a scan plus sort.
- Tests: none changed. Existing tests use random unique emails with exact lookups, so they still pass and say nothing about the new semantics. The 7 touched steps marked "tested" are not tested for this behaviour.

### Questions to ask
1. **recover-forgotten-password → sets new password:** say I sign up as `admin0@mine.io` (I sort before `admin@example.com`) and request `/password-recovery/admin`, so the link comes to me with `sub="admin"`. Then I change my email (`PATCH /users/me`) or delete my account (`DELETE /users/me`). Redeeming the token now resets `admin@example.com`'s password. Isn't that an account takeover of anyone whose prefix an attacker can sort ahead of? Why does `get_user_by_email` need to change at all for an admin search?
2. **sign-in → logs in:** have you checked production for emails that contain `_` or `%`, or that are a prefix of another user's email? Those users can now be resolved to someone else and fail login. Signup and email-change can also be refused for them.
3. **Alternatives:** the simpler version keeps `get_user_by_email` as `User.email == email` and confines prefix matching to the admin-only `search_users`. What did that version not give you?
4. **Admin searches users (new step):** should `q` be `startswith(q, autoescape=True)` so `%` doesn't mean "everyone"? Should `limit` be capped? Should `count` be the total, as in `GET /users/`, before a frontend relies on it?
5. **Failure / performance:** how many users are in production, and did you measure login latency now that the email lookup can't use the unique index?
