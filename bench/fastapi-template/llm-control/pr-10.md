# PR-10 review: "security: standardise on bcrypt (argon2 wheels fail on our ARM build)"

**What it does:** Removes `Argon2Hasher` from the `pwdlib` `PasswordHash` so it only has `BcryptHasher` (`backend/app/core/security.py`), and swaps `crud.DUMMY_HASH` from an argon2 hash to a bcrypt hash.

**Existing behaviour that changes:**
- On `main`, argon2 is the primary hasher. New users get `$argon2id$` hashes, and legacy bcrypt hashes get upgraded to argon2 on login (`verify_and_update`). So most stored `user.hashed_password` values in production are argon2, including the first superuser's.
- With this PR, `pwdlib` can no longer identify those hashes, so `verify_and_update` raises `UnknownHashError`. I checked this with pwdlib 0.3.1. Nothing catches it: there's no try/except and no exception handler. As a result:
  - `POST /login/access-token` returns a 500 for every argon2 user, whether the password is right or wrong. Existing users, admins included, are locked out.
  - `PATCH /users/me/password` returns a 500 for the same users, because it also calls `verify_password` on the stored hash.
  - The only way back in is the email reset flow (`/reset-password/`), which writes a new bcrypt hash without checking the old one. That only works if SMTP is configured in production.
- New hashes are bcrypt (rounds=12, `$2b$`). `bcrypt==5.0.0` (pinned in `uv.lock`) raises `ValueError` for passwords over 72 bytes. The models still accept passwords of up to 128 characters (`max_length=128`), so signup, create-user, update and reset with a long password now return a 500. On `main` that worked, because argon2 has no such limit.
- The PR doesn't fix the reason it gives: `pyproject.toml` still requires `pwdlib[argon2,bcrypt]`, so `argon2-cffi` is still installed on the ARM build.
- Tests weren't updated. `tests/api/routes/test_login.py::test_login_with_bcrypt_password_upgrades_to_argon2` and `::test_login_with_argon2_password_keeps_hash` assert `$argon2` prefixes, so they will fail (or error).

**Questions for the author (ranked):**
1. What happens to the existing argon2 hashes in the production `user` table? As written, every one of those users, including the superuser, gets a 500 on login and on password change. Should `Argon2Hasher` stay in the tuple for verification only, with bcrypt first so it's used for new hashes? Or is there a migration or forced-reset plan, with SMTP confirmed working?
2. Did the ARM build actually get fixed? `pyproject.toml` / `uv.lock` still pull in `pwdlib[argon2]` → `argon2-cffi`. If the wheel is the problem, this diff doesn't remove it. If it isn't, why drop argon2 verification at all?
3. How should passwords longer than 72 bytes be handled under bcrypt 5.0.0? Today the API accepts up to 128 characters, and these now return a 500 on signup, reset or update. Do we lower `max_length`, pre-hash, or return a 4xx? This is a client-visible validation contract change either way.
4. Should a hash format we can't verify produce a 401/400 instead of a 500? Should `verify_password` catch `UnknownHashError`, so the login failure looks the same as a wrong password and doesn't reveal account state?
5. Can you update the argon2-specific tests in `test_login.py` and add one that logs in a user with a pre-existing `$argon2id$` hash? Right now CI should be red.

VERDICT: do-not-merge
