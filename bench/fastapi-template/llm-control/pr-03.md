# Review: pr-03 — "deps: inactive users are already refused at login"

**What it does:** Removes the `if not user.is_active: raise HTTPException(400, "Inactive user")` check from `get_current_user` in `backend/app/api/deps.py`, so token-authenticated requests no longer check whether the user is active.

**What existing behaviour changes:**
- The commit message is only partly true. `/login/access-token` does refuse inactive users, but only when it issues a token. Tokens are stateless HS256 JWTs that last `ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*8` (8 days), and nothing revokes them. Until now, the per-request check in `get_current_user` was the only thing that stopped a deactivated user. After this change, deactivating a user does nothing to tokens they already hold, for up to 8 days.
- Every `CurrentUser` route is affected: `/users/me` (GET/PATCH/DELETE), `/users/me/password`, `/users/{id}`, all of `/items/*`, and `/login/test-token`. A deactivated user can still read, create, edit and delete items, and can change their email and password.
- `get_current_active_superuser` builds on `get_current_user` and checks only `is_superuser`, so despite its name it stops checking "active" too. A deactivated superuser keeps full admin rights until their token expires. That covers `/users/` list and create, `PATCH /users/{id}`, `DELETE /users/{id}`, `/utils/*` and `/password-recovery-html-content`. They can even call `PATCH /users/{own id}` with `{"is_active": true}` and reactivate themselves.
- Existing data: some production users are already `is_active=False` and may still hold a token issued in the last 8 days. Those tokens start working again as soon as this deploys. The admin UI (`EditUser.tsx`) still shows "Inactive", which is now misleading.
- Clients: requests that used to get `400 "Inactive user"` now succeed. The frontend never handled that 400 specifically (it only clears the token on 401/403), so nothing visibly breaks. That is also why the regression is easy to miss.
- No test covers the removed branch (`backend/tests` has no inactive-user API test), so CI will pass.

**Questions for the author (ranked):**
1. Deactivation is now ignored for any token issued before it, for up to 8 days, and nothing else revokes JWTs. How should an admin cut off a compromised or offboarded account immediately after this change? If it can't be done, what is this change for?
2. A deactivated superuser now keeps full admin access, and `PATCH /users/{id}` lets them set `is_active=true` on themselves. Was that intended? Should `get_current_active_superuser` check `is_active` itself?
3. Some `is_active=False` users in production may already hold tokens from the last 8 days, and those tokens become valid again on deploy. Have you checked how many exist, or planned to rotate `SECRET_KEY` / shorten token lifetime at rollout?
4. What problem prompted this change: performance, a bug, or just removing a duplicate check? The cost is one attribute read on a row that is already loaded. Could a narrower change solve the real issue?
5. If you keep the change, will you add an API test that pins the intended behaviour for an inactive user with a valid token, and rename `get_current_active_superuser` (or document the change) so callers don't assume it checks "active"?

VERDICT: do-not-merge
