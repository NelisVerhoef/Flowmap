# Review: pr-16 "users: rely on ON DELETE CASCADE for a user's items"

**What it does:** Removes the explicit `DELETE FROM item WHERE owner_id = :user_id` from the superuser `DELETE /users/{user_id}` endpoint (backend/app/api/routes/users.py), so the endpoint now only calls `session.delete(user)`.

**What existing behaviour changes:**
- Data outcome: none. The user's items are still deleted in the same transaction. `User.items` is declared with `Relationship(cascade_delete=True)`, which SQLModel maps to SQLAlchemy `cascade="all, delete-orphan"`. `passive_deletes` is not set, so on flush the ORM SELECTs the user's items and DELETEs them before it deletes the user row. `item.owner_id` also has `ondelete="CASCADE"` in the model, and migration 1a31ce608336 adds it to the database, so the DB cascade is there as a backstop.
- API contract: none. Same status codes, the same 403/404 checks and the same `Message` body. No frontend or client change is needed.
- Mechanism and cost: before, the items went in one bulk DELETE. Now every item row is loaded into the session and deleted by primary key. This is slower and uses more memory when a user owns many items. It is the same path that `DELETE /users/me` already uses in production, so the change makes the two delete endpoints consistent.
- The commit message is inaccurate: as written, the code relies on the ORM cascade, not on the database's ON DELETE CASCADE.

**Questions for the author (ranked):**
1. The title says "rely on ON DELETE CASCADE", but without `passive_deletes` SQLAlchemy loads and deletes each item itself, and the DB cascade never fires on this path. Which mechanism did you mean? Is the switch from one bulk DELETE to load-then-delete-per-row OK for users with very many items (risk of slow admin deletes or timeouts)? If you meant the DB cascade, `passive_deletes="all"` on `User.items` would do it, as a separate change.
2. Can you confirm production is at Alembic head (at least 1a31ce608336), so the `item_owner_id_fkey` constraint really has ON DELETE CASCADE? This matters for the claim in the title and as the backstop for an item inserted at the same time as the delete.
3. No test deletes a user who owns items, on either delete endpoint. Can you add one: a superuser deletes a user with items, gets 200, that user's items are gone and other users' items are untouched?
4. Do any production users own a very large number of items? If so, have you timed the new path against a realistic row count?

VERDICT: safe-to-merge
