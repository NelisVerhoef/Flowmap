# Review: pr-07 "models: reuse UserBase fields for registration"

**What it does:** `UserRegister` now inherits from `UserBase` (not `SQLModel`), dropping its own `email` and `full_name` fields. The stated goal is to cut duplicated fields.

**What existing behaviour changes:**
- `UserBase` also has `is_active` and `is_superuser`, so `UserRegister` now accepts both. Before, they were not declared and were silently ignored.
- `POST /api/v1/users/signup` is public (no auth). It passes the input straight through: `UserCreate.model_validate(user_in)` -> `crud.create_user` -> `User.model_validate(...)`. So a request body like `{"email": ..., "password": ..., "is_superuser": true}` now creates a **superuser**. Any anonymous person can take admin rights: list, edit and delete all users and items. This is a privilege-escalation hole in production.
- The OpenAPI schema for `UserRegister` gains `is_active` and `is_superuser`. A regenerated frontend client (`frontend/src/client/types.gen.ts`) would advertise them. Existing clients that send only email, password and full_name keep working.
- No tests were added. The existing `test_register_user` does not send `is_superuser`, so it still passes and does not catch the problem.

**Questions for the author (ranked):**
1. Did you mean for `/users/signup`, which needs no login, to accept `is_superuser` and `is_active` from the request body? As written, anyone can sign up as a superuser. How do you plan to stop that: keep `UserRegister` separate, or use a narrower shared base that has only email and full_name?
2. Can you add a test showing that `POST /users/signup` with `"is_superuser": true` (and `"is_active": false`) still creates a normal, active user?
3. Will you regenerate the frontend client? The new schema would show the privileged fields to every API consumer.
4. Were any accounts in a deployed environment created through signup while this branch was running? If so, do we need to check for `is_superuser=true` users created there?

VERDICT: do-not-merge
