# Review: pr-15 — "models: cap item titles at 100 chars to fit the new card layout"

**What it does:** Changes `ItemBase.title` from `max_length=255` to `max_length=100` in `backend/app/models.py`. That one line, with no migration, data fix, test or frontend change.

**Existing behaviour that changes:**
- `ItemBase` is not only the input schema. `ItemCreate`, the `Item` table model **and the `ItemPublic` response model** all inherit from it, so the 100-char cap also applies to every response.
- **Reads of existing data break.** The `item.title` column is still VARCHAR(255), and the API accepted titles of 101–255 chars until now. `read_items` calls `ItemPublic.model_validate(item)` on every row, which raises `ValidationError` (I reproduced this with sqlmodel 0.0.47). So one legacy long title makes `GET /items/` return 500 for its owner's whole list and for any superuser page that includes it. `GET /items/{id}` hits the same check in response validation and also returns 500.
- **The update path is now inconsistent.** `ItemUpdate.title` still allows 255. A `PUT` with a 101–255-char title passes input validation, is **committed**, and then fails response validation with a 500. The client sees an error for a write that actually happened, and that item now breaks the owner's list. Even a clean database can pick up "poison" rows after the merge this way.
- **Create contract tightens.** `POST /items/` with a 101–255-char title now returns 422 where it used to return 200, and the OpenAPI schema changes. The frontend zod schemas in `AddItem.tsx`/`EditItem.tsx` have no max, so UI users get a raw server error.
- **Schema drift.** SQLModel metadata now says VARCHAR(100) while the DB says VARCHAR(255). Alembic runs with `compare_type=True`, so the next `--autogenerate` will emit `ALTER item.title TYPE VARCHAR(100)`. That will fail at deploy (prestart runs `alembic upgrade head`) if any longer title exists, or lose data if someone "fixes" it with truncation.
- The stated motive ("new card layout") is not in this PR. The items page still renders `DataTable`/`columns.tsx`, so a display cap could be done in the UI instead.

**Questions for the author (ranked):**
1. How many production `item` rows have `length(title) > 100`, and what happens to them? With this change every such row makes the owner's item list and the admin list return 500. Do you plan a backfill/truncation migration, or should the cap apply only to input (`ItemCreate`) and leave `ItemPublic` and the table model alone?
2. Why does `ItemUpdate.title` still allow 255? As written, a PUT with a 150-char title commits and then returns 500. Should it be 100 as well, and can you add a test for create, update and list at 101 chars?
3. Is there an Alembic migration for the column length? If not, how will you stop the next autogenerate from emitting VARCHAR(255)->VARCHAR(100), which fails or truncates on existing data?
4. Which API clients (beyond our frontend) create items, and do any send titles over 100 chars? This is a breaking 422 for them. Do you plan a deprecation or version note, and will you regenerate the frontend client and add a matching zod `.max(100)`?
5. Where is the card layout? If the 100-char limit is only about display, why not truncate in the UI and leave the API/storage contract as it is?

VERDICT: do-not-merge
