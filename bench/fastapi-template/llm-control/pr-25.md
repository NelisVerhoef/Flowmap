# Review: pr-25 "config: align reset-link lifetime with the email copy"

**What it does:** Changes the default `EMAIL_RESET_TOKEN_EXPIRE_HOURS` in `backend/app/core/config.py` from 48 to 336 (14 days). The comment says this is so the setting matches an email that says the link lasts two weeks.

**What changes for the existing system:**
- The stated reason is wrong. No email says "two weeks". `reset_password.html` (and its source, `packages/react-email/emails/reset_password.tsx`) says "This link will expire in {{ valid_hours }} hours", and `generate_reset_password_email` fills that in from this same setting (`backend/app/utils.py:80`). The email and the token have always agreed. The words "two weeks" do not appear anywhere in the repo's history.
- Every deployment that uses the default now issues password-reset JWTs that stay valid for 14 days instead of 48 hours. `compose.yml`, `compose.deploy.yml`, `.env` and the deploy workflows never set this variable, so production picks up the new default without anyone choosing it.
- Reset tokens are stateless and can be used more than once. `verify_password_reset_token` checks only the signature and `exp`. Nothing ties a token to the current password hash, marks it as used, or revokes it. A link still works after it has been used, and after the password changes, until it expires. This PR stretches that replay window 7x. Anyone who gets hold of the email or URL (a forwarded email, a shared mailbox, browser history, proxy or referrer logs) can take over the account for two weeks. The superuser endpoint `/password-recovery-html-content/{email}` also mints these longer-lived tokens.
- The email users see now reads "This link will expire in 336 hours."
- What does not break: tokens already issued keep the `exp` baked into them, there is no schema or data change, and the API contract and frontend are unchanged. Existing tests still pass because nothing asserts the lifetime.

**Questions for the author (ranked):**
1. Where is the "valid for two weeks" email copy? In this repo the email gets its hours from this same setting, so there was nothing out of sync. If production uses a different template that lives outside the repo, please point to it. Otherwise, what problem does this fix?
2. Reset tokens are reusable and are not invalidated when the password changes. Is a 7x longer window, during which a leaked reset link can take over an account, an accepted security decision? Has security or product signed off on 14 days? If longer links really are needed, would you first add single-use or hash-bound tokens (for example, include a fingerprint of the password hash in the claims and check it on reset)?
3. Should this be a per-deployment env override instead of a new default? `EMAIL_RESET_TOKEN_EXPIRE_HOURS` is not passed through in `compose.yml` or `compose.deploy.yml`, so right now every deployment gets 14 days without choosing it.
4. Is "This link will expire in 336 hours" the copy you want users to see? If two weeks is the goal, the template should say so in days.
5. Can you add a test that pins the token lifetime (and the hours shown in the email), so a future change to this default is deliberate?
